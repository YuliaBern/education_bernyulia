# ﻿**ЛАБОРАТОРНА РОБОТА № 3**

**Тема:** Моделювання взаємодії сервісів 

**Мета:** Змоделювати потоки даних у системі

**Короткі теоретичні відомості**

У розподілених системах взаємодія між мікросервісами відбувається двома основними способами: синхронною та асинхронною.

Синхронна взаємодія передбачає, що один сервіс надсилає запит іншому і чекає на відповідь у реальному часі. Найпоширеніші технології:

-REST over HTTP/HTTPS — простий, універсальний, добре підходить для взаємодії з зовнішніми клієнтами та веб-додатками;

-gRPC — високопродуктивний протокол на базі HTTP/2 і Protocol Buffers, використовується переважно для внутрішньої взаємодії між мікросервісами завдяки меншій затримці та меншому обсягу трафіку.

Асинхронна (подійно-орієнтована) взаємодія працює через брокери повідомлень (message brokers): RabbitMQ, Apache Kafka, NATS, Redis Streams тощо. Сервіс-видавець публікує подію або повідомлення в чергу/топік і продовжує роботу, не чекаючи відповіді. Один або кілька сервісів-споживачів асинхронно обробляють цю подію. Такий підхід забезпечує слабке зв’язування, високу стійкість до збоїв та легке горизонтальне масштабування.

Для візуалізації порядку обміну повідомленнями та запитами використовується Sequence Diagram (діаграма послідовності UML). Вона показує учасників (акторів та сервісів), послідовність викликів, синхронні та асинхронні повідомлення, а також час життя об’єктів.

Для опису фізичного розгортання системи застосовується Deployment Diagram (діаграма розгортання UML). На ній відображаються вузли (сервери, контейнери, Kubernetes-кластери), артефакти (Docker-образи сервісів), бази даних, брокери повідомлень та зв’язки між ними.

**Завдання до роботи згідно варіанту**

Вибраний сценарій:

«Техніка вийшла з ладу під час роботи → потрібно швидко перенаправити задачу на іншу одиницю техніки та повідомити механіка». Типовий критичний сценарій на будівельному майданчику. У системі беруть участь три мікросервіси (з лабораторної №2):

Equipment Service

Allocation Service

Maintenance Service

**Завдання**

1\. Вибрати сценарій (наприклад, подання звіту з будівельного майданчика). 

Кран № 17 перестав піднімати вантаж → датчик/оператор фіксує поломку → система автоматично:

- блокує цю техніку,
- знаходить вільну заміну,
- переназначає задачу,
- створює заявку на ремонт,
- сповіщає механіка.

2\. Описати послідовність взаємодії сервісів у вигляді Sequence Diagram. 

```plantuml

@startuml

title Обробка поломки техніки

actor Оператор

participant Мобільний\_додаток as App

participant API as Gateway

participant Equipment\_Service as Eq

participant Allocation\_Service as Alloc

participant Maintenance\_Service as Maint

Оператор -> App: Повідомляє про поломку

App -> Gateway: reportFailure()

Gateway -> Eq: reportFailure()

Eq -> Eq: Оновлення статусу = BROKEN

Eq -> Alloc: notifyBroken(техніка 17)

Eq -> Maint: notifyBroken(техніка 17)

Alloc -> Alloc: Переназначення задачі\nна іншу техніку

Maint -> Maint: Створення заявки на ремонт

Maint -> Оператор: Повідомлення: "Заявку створено"

@enduml

```

3\. Вказати тип взаємодії (HTTP/gRPC/Message Queue). 

|**Джерело → Отримувач**|**Тип взаємодії**|**Технологія**|**Пояснення**|
| :-: | :-: | :-: | :-: |
|Клієнт → Equipment Service|Синхронна|REST (HTTPS)|Оператор отримує миттєве підтвердження фіксації поломки|
|Equipment Service → Kafka|Асинхронна|Apache Kafka|Публікується подія EquipmentStatusChanged|
|Kafka → Allocation Service|Асинхронна|Apache Kafka|Автоматично переназначає задачу на іншу техніку|
|Kafka → Maintenance Service|Асинхронна|Apache Kafka|Автоматично створює заявку на ремонт і сповіщає механіка|

4\. Побудувати Deployment Diagram із зазначенням контейнерів.

```plantuml

@startuml

title Deployment Diagram — Система керування технікою

node "Сервер застосунку" {

`  `[API Gateway]

`  `[Equipment Service]

`  `[Allocation Service]

`  `[Maintenance Service]

}

node "Брокер повідомлень" {

`  `[Kafka]

}

node "Бази даних" {

`  `database "PostgreSQL"

`  `database "MongoDB"

`  `database "Redis (cache)"

}

node "Клієнти" {

`  `[Мобільний додаток]

`  `[Пристрій механіка]

}

[Мобільний додаток] --> [API Gateway] : HTTPS

[Пристрій механіка] --> [API Gateway] : HTTPS

[API Gateway] --> [Equipment Service]

[API Gateway] --> [Allocation Service]

[API Gateway] --> [Maintenance Service]

[Equipment Service] --> PostgreSQL

[Allocation Service] --> PostgreSQL

[Allocation Service] --> Redis

[Maintenance Service] --> MongoDB

[Equipment Service] --> Kafka : publish

Kafka --> [Allocation Service] : consume

Kafka --> [Maintenance Service] : consume

@enduml

```

**Висновки**

У ході виконання лабораторної роботи №3 було успішно змодельовано взаємодію мікросервісів системи керування технікою на будівельному майданчику на прикладі критичного сценарію «Поломка техніки → автоматичне переназначення задачі та створення заявки на ремонт». Отримані моделі (Sequence Diagram та Deployment Diagram) повністю відповідають принципам мікросервісної архітектури та можуть бути безпосередньо використані на етапі проєктування й реалізації реальної системи керування технікою на будівельному майданчику.
