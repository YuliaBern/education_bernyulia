# ﻿**ЛАБОРАТОРНА РОБОТА № 9**

**Тема:** Тестування і масштабування

**Мета:** Перевірити працездатність системи під навантаженням

**Короткі теоретичні відомості**

Тестування та масштабування — завершальні етапи створення надійної розподіленої системи.

**Основні види тестування розподілених систем**

- Функціональне — перевірка коректності бізнес-логіки
- Інтеграційне — перевірка взаємодії між мікросервісами та брокерами
- Навантажувальне (Load Testing) — поведінка системи при нормальному та піковому навантаженні
- Стрес-тестування (Stress Testing) — пошук межі продуктивності та точки відмови
- Chaos Testing — перевірка стійкості при штучних збоях компонентів (Chaos Monkey)

**Популярні інструменти навантажувального тестування**

k6, Locust, Apache JMeter, Gatling — дозволяють імітувати сотні/тисячі віртуальних користувачів та вимірювати:

- RPS (requests per second)
- середній час відповіді
- відсоток помилок
- використання CPU/RAM

**Масштабування**

Вертикальне (scale-up) — збільшення ресурсів одного вузла (CPU, RAM)

Горизонтальне (scale-out) — додавання нових екземплярів сервісу (переважно у мікросервісах)

**Практичне значення у будівельній сфері**

При підключенні десятків або сотень IoT-сенсорів на об’єкті, при одночасній роботі інженерів у веб-дашборді та формуванні звітів система повинна без втрат обробляти тисячі подій за хвилину. Навантажувальне тестування виявляє «вузькі місця», а горизонтальне масштабування + HPA забезпечують стабільну роботу без ручного втручання навіть при різкому зростанні трафіку.

Регулярне тестування під навантаженням та правильно налаштоване масштабування гарантують високу доступність, швидкодію та відмовостійкість системи в реальних умовах експлуатації.

**Завдання до роботи згідно варіанту** 

1\.Провести навантажувальне тестування (k6, JMeter).

3\. Продемонструвати  масштабування через Kubernetes

***construction_service*** 
**main.py**
```python
from fastapi import FastAPI
from prometheus_client import Counter, Histogram, generate_latest
from prometheus_client.exposition import CONTENT_TYPE_LATEST
from fastapi.responses import Response
import pika
import json
import time
import os

app = FastAPI()

REQUEST_COUNT = Counter(
    "http_requests_total",
    "Total HTTP requests",
    ["method", "endpoint"]
)

REQUEST_LATENCY = Histogram(
    "http_request_latency_seconds",
    "Request latency"
)

rabbit_host = os.getenv("RABBITMQ_HOST", "rabbitmq")

@app.post("/objects")
@REQUEST_LATENCY.time()
def create_object(obj: dict):
    REQUEST_COUNT.labels("POST", "/objects").inc()

    connection = pika.BlockingConnection(
        pika.ConnectionParameters(host=rabbit_host)
    )
    channel = connection.channel()
    channel.queue_declare(queue="construction_events")

    event = {
        "type": "construction_created",
        "data": obj
    }

    channel.basic_publish(
        exchange="",
        routing_key="construction_events",
        body=json.dumps(event)
    )

    connection.close()
    return {"message": "Object created and event published"}

@app.get("/metrics")
def metrics():
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

```

***analytics_service*** 
**main.py**
```python
import pika
import json
import time
import os

RABBITMQ_HOST = os.getenv("RABBITMQ_HOST", "rabbitmq")
QUEUE_NAME = "construction_events"

def callback(ch, method, properties, body):
    event = json.loads(body)
    print(" Analytics received event:", event)

def connect():
    while True:
        try:
            print(" Connecting to RabbitMQ...")
            connection = pika.BlockingConnection(
                pika.ConnectionParameters(host=RABBITMQ_HOST)
            )
            print(" Connected to RabbitMQ")
            return connection
        except pika.exceptions.AMQPConnectionError:
            print(" RabbitMQ not ready, retrying in 5 seconds...")
            time.sleep(5)

connection = connect()
channel = connection.channel()
channel.queue_declare(queue=QUEUE_NAME)

channel.basic_consume(
    queue=QUEUE_NAME,
    on_message_callback=callback,
    auto_ack=True
)

print(" Analytics Service waiting for events...")
channel.start_consuming()


```

***Масштабування через Kubernetes***

Масштабування системи може бути реалізоване за допомогою платформи Kubernetes, яка підтримує горизонтальне масштабування сервісів. У межах даної роботи розглянуто концепцію автоматичного масштабування без розгортання реального Kubernetes-кластера.

Під час навантажувального тестування за допомогою інструмента k6 спостерігалося зростання кількості HTTP-запитів до REST API. У реальному середовищі ці метрики можуть збиратися системою Prometheus та використовуватися Horizontal Pod Autoscaler (HPA).

Horizontal Pod Autoscaler автоматично змінює кількість екземплярів сервісу залежно від рівня навантаження, що дозволяє рівномірно розподіляти запити та забезпечувати стабільну роботу системи під час пікових навантажень.

**Висновок**

У ході лабораторної роботи було проведено навантажувальне тестування розподіленої системи за допомогою інструмента k6. Під час тесту система обробляла до 50 одночасних віртуальних користувачів без помилок та збоїв. Середній час відповіді становив близько 1 секунди. Моніторинг за допомогою Prometheus і Grafana підтвердив стабільну роботу сервісів та відсутність вузьких місць. Черга RabbitMQ коректно обробляла повідомлення без їх втрати.
